# L0 —— 用户给出的要求与 guide（最高优先，任何实现不得与之冲突）

> 层级：**L0 用户要求**。这里只记录由用户（operator）明确给出的要求/规范/结论。
> 不是客观事实、不是实验结论、也不是 agent 的推导（那三类在 L1/L2/L3）。

## 项目定位（用户给定）

1. 研究对象是**本地模型的各种设置 / 超参数选择对基准实际跑分的影响**。
2. **量化只是其中一个子项**；把整个项目说成"量化研究"是错的。
3. 每一项设置单列一项研究：该设置为自变量 **X**，基准分数为因变量 **Y**，其余被固定的量构成系列。

## 控制变量原则（用户给定）

4. 一个研究里**只有一个变量**；其余一切（provider、量化方案、解码协议等）必须**固定一致**。
5. 以"量化位宽"为例：变量是 **bpw**；因此 **provider 与量化方案必须一致**（要么都用 UD、要么都不用；
   要么都来自同一提供方）——"名字一致"是为了不让方案/来源成为隐藏变量，不是名字本身有意义。
6. **禁止**用 `Q2/Q3/Q4/Q5` 这类标称档位描述量化——它含糊（同名跨约 2.76–5.04 比特/权重），
   把方案与位数搅在一起。量化一律用真实**有效位宽**表述。

## 报告要求（用户给定）

7. 结构：**总 — 分 — 总**。开头总述（项目是什么、研究什么、X/Y 是什么）；中间每一项一节；结尾总结。
8. 每个"分"里至少包含：**原始数据表 → 由该表画出的图 → 分析/结论**。
9. **底层原始数据必须有表、且必须有图**；图必须能看懂（不得是一堆挤在一起的乱线；要有图例、坐标轴、标题）。
10. 结论可以有，也可以配图、可以有更高层的汇总图表与分析——但不是用结论去替代底层数据/图。
11. 文字用中文、人话；表格要专业、可读；排版要像论文，不能糊成一团。

## 文档要求（用户给定）

12. 文档必须**按来源分层**，不同层不得混写成一层：
    - **L0** 用户给出的要求 / guide（本文件）
    - **L1** 客观规范与事实（方法、名字、协议、环境、数据库规则等）
    - **L2** 客观实验得出的结论（测出来的）
    - **L3** agent 自己推导出的结论 / 建议
13. **SSOT**：测量数字只属于 `experiments.sqlite`；文字知识只属于 `docs/`；报告是派生视图，
    不得引入 docs 里没有的论断；同一事实不得两处各说一套。
