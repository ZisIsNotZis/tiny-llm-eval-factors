# a05 KV 缓存精度 — 本目录规则

本文件只写这个 subproject 自己的窄规则；通用法则在仓库根 `AGENTS.md` 与 `/home/z/vibe/AGENTS.md`，不在此复述。
里程碑、工作包、AC、判据与派工在 `PLAN.md`；已成立的事实与证据在 `RESULT.md`；复算装置在 `analysis/`。

## 这个轴的口径（违反一条，结论就作废）

1. **X 只有两个：KV 缓存的精度（K/V 数据类型）与 ctx 长度。** 权重位宽归 `a01`/`a03`，层比特分配归 `a04`，采样参数归 `a06`。想把权重位宽或采样塞进本轴的对照，就不是本层的实验。
2. **KV 是成对的 (K, V)，不是一个标量。** 每次报数都写 `f16/f16` 这种两段式；`q8_0` 单独出现就是缺陷。m30 的 16k 格已经给出「K 起作用、V 不起作用」的迹象，在 `WP4` 之前不得当结论。
3. **一格 = 一条完整协议串**：`protocol` 里的 `ctx= / kv= / fa= / prefix=` 都是设置本身。改了其中任何一段就是另一格，不许合并计数，也不许拿「同一模型的其它行」代替。
4. **不池化**：语言、协议（raw vs chat）、基准、ctx、KV 配置之间绝不平均。m30 只有 cpp 就只报 cpp。
5. **截断探针不与全量格比数值**：`n_items` 是 50 / 60 / 100 的格（`--limit`、60 题探针）只能与同一截断口径的格比；与 161/164 的格放在一起只能说方向。报告里 `(60)` 这个后缀就是在提醒这件事。
6. **「覆盖长上下文」必须有动态范围**：所有 KV 配置在最长 ctx 上都落在地板（0 或 1/n）时，该次测量判**不可分辨**并登记，不许写成「长上下文无差异」。地板的判据要先写下来再跑，不许跑完再挑解释。
7. **噪声与输入差严格分开（引用 `i01`）**：贪心 + 同提示集 + 同后处理版本时重复跑逐题相同（`i01::res32`，0 道题），所以组内不同设置的非零逐题差不是运行噪声；而 `i01::res29` 的 ±16/161 是「提示集/后处理变了」的量级，不用于本层任何组内比较。没有配对区间时只报计数，不报 p 值，也不写「相等」。
8. **判分口径先看清楚**：m130 面板的 `humaneval` 列是 **base** 判分，HumanEval+ 是另一个数（`i01::res31`）。逐题配对要两套各算一次，不许拿 base 的分去对 plus 的题。
9. **未测 ≥ 0 的优先级**：「没测」写「未测」+ 原因 + 代价；报告里的 `0.0` 格先查成因（生成失败、伪像、真 0 分是三种东西），查不清就登记，不改值。

## 入库纪律（写库是别人的活，本层先证明该不该写）

1. **只有 `migrate_db.py` 是入库路径**；真库要写时先做编号备份（`experiments.sqlite.bakN`），写入后跑完整性检查，并跑两次证明幂等。
2. **消费侧分不开的因子不得入库**：报告行标签（`make_report.mpl_protocol_label`）只保留 `ctx= / kv= / tmpl=`，所以带 `fa=` 的格一律先不入库，直到消费侧改了；判据与实测见 `RESULT.md::kv-m29-ingest-decision`。
3. **在库副本上证明影响，再谈写库**：改库前的影响评估一律用 `.tmp/` 下的副本（`analysis/kv_evidence.py` 的 F 段就是模板），真库只开 `mode=ro`。
4. 两条负控必须保持 PASS：`python3 checks/ingest_protocol_negative_control.py`、`python3 checks/ingest_skip_negative_control.py`。它们翻红说明入库路径本身坏了，那比任何数字都优先。

## GPU 与资源

1. 本层额度是 9% GPU / 5% CPU：一次只起一个占用 GPU 的作业，持有 `bash .wrapup/gpu_locked.sh`。锁只管本仓库；**绑定约束是 `nvidia-smi` 的 `memory.free`**，别的仓库的作业也在同一张卡上。
2. 起服前按实测算需求（模型文件 + KV 按 `-c` 与数据类型算 + compute buffer 余量），不套固定阈值；`memory.free` 不够就排队，不在前台等（`@scheduling.queue_behind`）。
3. 用 `llama-server` 时起服后断言 server 自报的 `n_slots` 与配置相符，不符即作废该次测量；用 `llama-passkey` 这类 CLI 时没有 `n_slots`，改为断言命令行里的 `-c`/`-ctk`/`-ctv` 与格子一致、且加载日志报告的 ctx 与 KV 类型相符。
4. 不改 vendor 运行时、不打补丁：采样或 KV 参数直接传给 llama-server / CLI。

## 数字纪律与装置

1. 每个数字后面跟证据路径与一条能被别人重跑的命令；跑不出来写「未测」和原因，不写 0、不写「估计」。
2. 所有数字由一条命令复算：`python3 "docs/subprojects/a05-KV 缓存精度/analysis/kv_evidence.py"`；它必须退出 0，`A05_SELFTEST=1` 时必须退出 1。改任何判据要同时改它。
3. `.scratch/originals/*` 已退役：那里的数只能标「不可复现」并写明原件已退役，不得当证据来源。
4. 复用 `.wrapup/mres/*` 的落盘产物前先确认它的 `run_tag`、`n`、协议串与当时的 server 参数；不确定就当未知。
5. 结论必须指回 `PLAN.md` 的 AC 之一；说不清服务哪条的工作不做。

4. **`a04` 的作业与本层共卡**：它持锁时排队，不抢、不 kill、不并发起服。
5. 不改别的 subproject 目录、不改 `docs/plan/subprojects.md`。
