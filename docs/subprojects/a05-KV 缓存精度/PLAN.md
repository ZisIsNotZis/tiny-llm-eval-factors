## 判定口径（先写死，避免事后挑解释）

1. **不池化**：语言、协议、基准、KV 配置、ctx 之间绝不平均。m30 只有 cpp，就只报 cpp。
2. **截断探针不与全量格比较**：`n_items = 50 / 60 / 100` 的格（m130 的 gsm8k·ifeval、m30 的 60 题、`--limit` 面板）只能与同一截断口径的格比；与 161/164 的全量格放在一起只说方向，不说数值。
3. **两个口径必须同时报**：每一对 KV（或 FA）配置都要给「分数差」与「逐题丢/得」两栏。分数差为 0 不等于逐题相同——m130 base 的 `q8_0→q4_0` 是 90 vs 90 却有 12 丢 12 得，m29 有 4 个格同样如此（`RESULT.md::kv-two-metrics`）。只有分数差而没逐题产物的格（m130 的 mmlu/gsm8k/ifeval，`i01::res26`）写「翻转未测」，不得写「无差异」。
4. **噪声地板（引用 `i01::res32`）**：贪心 + 同一提示集 + 同一后处理版本时，重复跑逐题相同（0 道题），所以同面板内不同设置的非零逐题差**不是**运行噪声；但它仍是单次抽样下的配置差，没有配对区间时只报计数，不报 p 值。
4. **输入差的量级（引用 `i01::res29`）不用于本层**：±16/161 是「提示集/后处理变了」导致的，本层所有组内比较都钉住了同一条 `protocol` 串的其余部分，所以它是不可比量级，不是本层地板。
5. **一格的测量身份包含协议串**：`protocol` 里的 `ctx= / kv= / fa= / prefix=` 是设置本身。哪个因子在报告行标签里被吞掉（`make_report.mpl_protocol_label` 只保留 `ctx= / kv= / tmpl=`），那个因子就**不得入库**，先让消费方学会它再谈入库。
6. **长上下文的「覆盖」必须有动态范围**：所有 KV 配置在最长 ctx 上都落到地板（0 / 1 out of n）时，该次测量判「不可分辨」，登记而不当结论；报告里出现的 `0.0` 格先查成因再读值（本层的 6 个 0.0 格成因见 `RESULT.md::kv-ctx-padded-floor`）。
7. **未测 ≠ 0**：`.scratch/originals/*` 已退役，那里的数只能标「不可复现」并写下原件已退役；本层不复用它们当证据。
8. **入 metric 之前先看判分口径**：m130 面板的 `humaneval` 列是 **base** 判分（`i01::res31` 说 EvalPlus 的 base/plus 是两个数），所以逐题配对必须两套都算一遍，不能拿 base 的分去对 plus 的题。
9. **写库纪律**：只有 `migrate_db.py` 是入库路径；真库要写时先做编号备份（`.bakN`），再跑两次证明幂等，并跑 `checks/ingest_*_negative_control.py` 两条负控。本层目前**不写库**（裁决见 `WP3`）。

## GPU 队列（未测，不是 0）

### WP4 的设计（写死在此，派工时原样执行；本层不跑）

**任务形态（针检索，不是代码生成）**：m30 的失败是模型续写填充前言，所以任务必须是「读出远端一个字串并原样回答」，且指令放在**最后一行**、要求只输出该字串。

- 每条 prompt = 填充段（`ctx − 1024` tokens，复用 `m30_build_pad.py` 的语料单位与 `/tokenize` 计数，不改它的代码）+ 一行针 `KEY: <5 位唯一数字>`，插在深度 `d ∈ {0.1, 0.5, 0.9}` + 最后一行指令 `Ignore the code above. Reply with the KEY value only (5 digits).`
- 判分：完成物里前 5 位数字与针一致即通过；其它（含继续写代码、空）判失败。
- 每格 20 条（20 个不同的针值 × 三种深度按 7/7/6 分配），`-np 1`、贪心、`n_predict 32`、`-fa on`（量化 V 需要 FA）。
- 网格：ctx {8192, 16384, 32768} × KV {(f16,f16), (q8_0,f16), (f16,q8_0), (q8_0,q8_0)} = **12 格**；每格同一 ctx 的填充段与针深度序列跨 KV 逐字节相同。
- **阳性对照 1 格**：ctx 8192，针放在深度 1.3（即超出窗口被截掉）→ 必须 0/20。它为整个设计提供「打分器能看到失败」的证明（`@gate_probe`）。
- **动态范围门（跑前写死，跑后不改）**：f16/f16 在 32768 上必须在 8–19/20 之间（既不顶天花板也不落地板）。20/20 → 升 49k 或把最深插到 0.98；≤7/20 → 把最高档降到 16k。对照格不是 0/20 → 打分器坏了，整轮作废重跑。
- **预算（按实测算，不拍阈值）**：提示处理中位 23 800 tok/s、最小 20 795（`.wrapup/m30b.log` 的 480 条 >4000 token `prompt eval time`）；生成 266 tok/s（`.wrapup/m30_32.log`）→ 32 token ≈ 0.12 s。每条 prompt 的 token 数就是 `ctx − 1024`。于是：32k 每条 ≈ 32768/23800 + 0.12 = **1.50 s**，16k ≈ 0.81 s，8k ≈ 0.47 s；每格 20 条 → 29.9 / 16.2 / 9.4 s；4 个 KV 合计 **222 s**，加对照 10 s 与一次冒烟 60 s ≈ **5 GPU 分钟**，预算上限 30 分钟（含 2 次重跑）。整轮提示 token = 4 × 20 × (8192+16384+32768) = **4.59 M tokens**。
- 对照锚点（同一模型的实测整格墙钟，含 768 token 生成）：m30 的 60 题格在 8k/16k/49k 上分别 168 / 210 / 337 s，与上面的吞吐推算同量级。
- **「两者仍然全同」怎么记（这本身有信息量）**：若 q4_0 与 f16 在三个 ctx 的全部 240 个逐题判定上完全相同，写成「在 ≤32k、针位于 10%/50%/90% 深度的检索任务上，q4_0 与 f16 的逐题判定完全相同；20 条/格下可见性下限是 >2/20 的差」，并同时写两条边界：(1) 这是**天花板**情形，只给出「该设计下未测出」，不给「长上下文无效应」；(2) 降一档用连续指标复核——`llama-perplexity -c <ctx> -ctk/-ctv` 在同一固定长语料上给 ΔPPL（连续、无天花板），每格 1 个 chunk、1.4 s/32k，12 格再加 ≤2 分钟。
- 可选交叉验证：`llama-passkey`（vendor 二进制）在同一 ctx/KV 上跑一遍作为第二个仪器；它的采样数与针位置未经验证，跑前先看它自己打印的行为，不能当唯一依据。
