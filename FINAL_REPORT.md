# Quantisation vs benchmark scores for local LLMs — definitive synthesis

*Reader-facing final report of the study. Every number names its `run_tag`; all values come from
`experiments.sqlite` and are reproduced by the generated reports
`.wrapup/out/MULTIPLE.md`, `.wrapup/out/LADDER_TOOLS.md`, `.wrapup/out/HORIZON.md`,
`.wrapup/out/PPL_REPORT.md`, `.wrapup/out/REANALYSIS.md`, `.wrapup/out/MOE_STRUCTURE.md`
(scripts: `multipl_e_analysis.py`, `ladder_analysis.py`, `horizon_analysis.py`,
`ppl_analysis.py`, `reanalysis.py`, `claims_ledger.py`), by the cross-benchmark analysis
(`bpw_sensitivity.py`, `bpw_paired.py`), and by the results tables in
`RESULTS_BY_COMPARISON.md` (generated by `.wrapup/mktables.py`).
Operational/harness detail lives in `OPERATIONS.md`; the rules live in `RESEARCH_METHOD.md`.*

**Headline.** Quantisation damage is strongly **benchmark-dependent**: per +1 effective bpw a
model loses ~0.17 of its GSM8K score and ~0.10 of its code score but ~0.02 of its TruthfulQA
score, and a paired test across 18 model families puts the capability-vs-knowledge gap at
**+0.120 per bpw, 95% CI [+0.039, +0.201]** (§3 F9). Sensitivity is a vector, not a number, and
multiple-choice knowledge — above all TruthfulQA — is the last thing to degrade, so it is the
worst benchmark for judging a quant.

---

## 1. The question

How does quantisation map onto **measured task scores** for local LLMs — across model size, model
type (dense/MoE), architecture, task type and decoding — under one controlled protocol? The
quantised-LLM community publishes **perplexity** as its headline quality number; PPL is a reference
only (vendors publish it as marketing; we are filling the missing quant↔score gap). This is a factor
study with explicit error bars, not a leaderboard. Non-goals: model recommendations as products,
self-training, beating PPL.

## 2. Method, and why the numbers are trustworthy

- **Item-level CIs everywhere.** A benchmark item is a Bernoulli trial, so a quant step's uncertainty
  is `SE = sqrt(p(1-p)/n + p'(1-p')/n')` over **items**. CIs computed over languages/categories
  (n = 2–5) are ~10× too narrow and produced two false claims (see §5).
- **The floors are measured, not assumed.** Greedy code is reproducible run-to-run (W1, sd 0.0);
  agentic multi-turn drifts ±0.015 (m15 0.095 vs m19 0.110, same config); a single HumanEval pair can
  only resolve |Δ| ≳ 0.03.
- **Protocol is recorded and never mixed** — raw-completion vs chat vs native-tools; forced-JSON vs
  native calling. Protocol alone has flipped the sign of quant conclusions twice (§3-F8).
- **Official harnesses, and more than one task type.** EvalPlus 0.3.1 for **HumanEval / MBPP** and
  their stricter **+** variants (the full 164/378 problem sets, not a subset), a local MultiPL-E
  suite, and lm-evaluation-harness 0.4.13 for **MMLU, ARC-Challenge, TruthfulQA-mc2, GSM8K and
  IFEval**. The tool-calling work (BFCL single- and multi-turn) was completed earlier and is kept
  in the DB as history; it is retired from the main tables because the operator's requirement is
  that every conclusion be measured on more than one standard benchmark, and the seven above span
  code / knowledge / truth / reasoning / instruction.
- **Coverage**: 44 models, 42-44 of them on each of the four code columns and 40-44 on each of the
  five lm-eval columns; 12-14 independent model families per within-family slope. 0.8B-35B, dense
  and MoE, ~2.2-6.2 effective bpw.

**Five silent-failure classes were found and fixed** (each yields plausible-but-wrong numbers):

| # | class | what it produced |
|---|---|---|
| 1 | stale BFCL result reuse (`generate` keys by handler, not run) | would have faked a "Q3≈Q2" null |
| 2 | orphaned `llama-server` holding the inherited `flock` | stalled the queue ~36 min–59 h |
| 3 | non-idempotent ingest | dropped hour-long panels on re-run |
| 4 | wrong-model server on the port | attribution to the wrong checkpoint |
| 5 | grader dialect ≠ model's tool-call dialect | 0.00% for a model that calls tools fine |

**Rule adopted:** a `0.00` score is attributed to the harness first, never to capability (m12/m14:
granite Q2_K 0.00 persists under the correct handler and is a *real* cliff; granite Q3 0.00 was a
handler dialect artifact).

### F2 — the quant curve is a **step, then a plateau**

`Qwen3.5-2B`, MultiPL-E pooled (`ladder_analysis.py` → `.wrapup/out/LADDER_TOOLS.md`, `run_tag='m3-quant-ladder'`):

| quant | pooled score | note |
|---|---|---|
| UD-IQ2_XXS | 0.006 | **collapsed** (1 language only) |
| UD-IQ2_M | 0.139 | ≈ Q2 |
| UD-Q2_K_XL | 0.120 | |
| **UD-Q3_K_XL** | **0.275** | the one big step |
| UD-Q4_K_XL | 0.284 | ≈ Q3 |
| UD-Q5_K_XL | 0.277 | ≈ Q3 |

Steps: `IQ2_M→Q2` **−0.019**, `Q2→Q3` **+0.155 [+0.107, +0.204]**, `Q3→Q4` **+0.008 [−0.016, +0.033]**,
`Q4→Q5` **−0.006 [−0.057, +0.045]**. The aggregate matched-context re-analysis agrees: the

(Caveat in F3: for some families Q4 still helps.)

### F3 — the `Q2` floor: at 2B every hard agentic category pins to ~0.005; the deficit is headroom-limited, not a law

Complete Qwen3.5 matrix, item-level (`m3`/`m1`/`m2` code; `m4b` tool single-turn; `m9`/`m11`/`m17`
multi-turn):

| anchor | axis | Q2 | Q3 | deficit |
|---|---|---|---|---|
| 2B | code (MultiPL-E) | 0.120 | 0.275 | **0.155** (m3) |
| 2B | tool single-turn | 0.299 | 0.502 | **0.202** (m4b) |
| 2B | tool multi-turn | 0.025 | 0.185 | **0.160** (m9) |
| 4B | code | 0.314 | 0.457 | **0.142** (m1) |
| 4B | tool single-turn | 0.615 | 0.691 | **0.077** (m4b) |
| 4B | tool multi-turn | 0.385 | 0.535 | **0.150** (m11) |
| 9B | code | 0.429 | 0.571 | **0.143** (m2) |
| 9B | tool multi-turn | 0.490 | 0.650 | **0.160** (m17) |
| 35B-MoE | multi-turn base | 0.600 | 0.675 | **0.075** (m20) |

**The deficit ranges ~0.077–0.202 — there is no constant.** It is **headroom-limited**: 4B
single-turn has the smallest deficit precisely because Q2 is already near its own ceiling (0.615 vs
0.691); the 35B MoE is the same (0.600 vs 0.675). The crisp invariant is the **floor** — at 2B, BFCL
multi-turn (`run_tags m9/m18/m19`, 200 items each):

| category | Q2 | Q3 | deficit |
|---|---|---|---|
| `multi_turn_base` | 0.025 | 0.185 | 0.160 (m9) |
| `multi_turn_miss_param` | 0.005 | 0.105 | 0.100 (m18) |
| `multi_turn_long_context` | 0.005 | 0.110 | 0.105 (m19) |
| `multi_turn_miss_func` | 0.005 | 0.080 | 0.075 (m18) |

At Q2 **every** hard agentic category sits at the floor (~0.005); Q3 lifts each to its own ceiling,
and the category ranking (`base > miss_param > long_context > miss_func`) is quant-invariant.

> **Correction trail (kept deliberately).** v1 said quant damage "scales with task horizon" — a
> *retention-ratio* artifact (the ratio varies only because the Q3 baseline varies). v2 said "the
> gain is a constant ~+0.15" — over-generalised from six cells; the 4B single-turn cell (0.077)
> disproves it. The honest claim is the one above: **deficit = headroom, with a genuine floor
> collapse at small size on hard agentic tasks.**

### F9 — quantisation damage is **benchmark-dependent**: capability tasks lose ~15x more per bpw than multiple-choice knowledge

This is the finding the multi-benchmark requirement was designed to expose, and it is the
largest single effect in the study.

**Method.** For every model family (same base weights, different quant) and every benchmark,
compute the within-family slope `d(score)/d(bpw)` over that family's own bpw ladder. Effective
bpw = `8 x file_bytes / n_params`; nominal `Q2`/`Q3` labels are never used because they span
2.76-5.04 bpw. Architecture and parameter count are held constant by construction, so bpw is
the only varied quantity. Slopes are then compared **paired inside each family**, which cancels
family-level variance — the pooled ranking alone could make a benchmark look sensitive merely
because sensitive models landed in its sample. Scripts: `bpw_sensitivity.py`, `bpw_paired.py`.

**Result — median sensitivity per +1 effective bpw, n = 16-18 families each:**

| benchmark | task type | median slope | mean slope | positive |
|---|---|---|---|---|
| **GSM8K** | arithmetic reasoning | **+0.168** | +0.222 | 14/16 |
| **IFEval** | instruction following | **+0.127** | +0.132 | 14/18 |
| **HumanEval+** | code | **+0.104** | +0.147 | 12/17 |
| **MBPP+** | code | +0.065 | +0.118 | 14/17 |
| **MMLU** | knowledge (MC) | +0.055 | +0.081 | 15/18 |
| **ARC-Challenge** | science QA (MC) | +0.027 | +0.043 | 10/16 |
| **TruthfulQA mc2** | truthfulness (MC) | **+0.017** | +0.021 | 13/18 |

A 10x spread between the most and least sensitive benchmark.

**Grouped paired test** — capability tasks (HumanEval+, MBPP+, IFEval, GSM8K) against
knowledge/truth tasks (MMLU, ARC-c, TruthfulQA), one paired difference per family:

> **mean difference +0.1201 per bpw, 95% CI [+0.0393, +0.2010], n = 18 families, 14/18 in that direction.**

Significant. Pairwise, the 95% CI on the paired difference excludes zero for:
`HumanEval+ > TruthfulQA +0.123`, `HumanEval+ > ARC-c +0.107`, `GSM8K > IFEval +0.095`,
`MBPP+ > TruthfulQA +0.094`, `MBPP+ > ARC-c +0.079`, `MMLU > TruthfulQA +0.060`,
`MMLU > ARC-c +0.045`; and in the other direction (the capability column is more sensitive)
`IFEval > MMLU`, `IFEval > ARC-c`, `IFEval > TruthfulQA`, `GSM8K > MMLU`,
`GSM8K > ARC-c`, `GSM8K > TruthfulQA` — the last by +0.200/bpw, the largest
single gap in the table.

**Worked example (one family, no aggregation at all).** `granite-4.1-3b`, 3.22 -> 4.94 bpw:

| benchmark | 3.22 bpw | 4.94 bpw | delta |
|---|---|---|---|
| HumanEval+ | 0.0854 | 0.7683 | **+0.683** |
| MBPP+ | 0.1349 | 0.6270 | +0.492 |
| IFEval | 0.4100 | 0.7900 | +0.380 |
| ARC-Challenge | 0.5100 | 0.5500 | +0.040 |
| TruthfulQA | 0.4313 | 0.5107 | +0.079 |

Same weights, same ladder, same harness: code moves by 0.68 and multiple-choice knowledge by
0.04. A study that measured only MMLU would have reported this model as barely affected.

**What this means in practice.** Sensitivity is not a single number per model — it is a vector,
and the benchmark you happen to own determines the answer you get. Code and
instruction-following are the early-warning signals; multiple-choice knowledge is the last
thing to go, so it is the *worst* choice for deciding how much a quant costs you. The
mechanism is consistent with the step/floor picture in F2-F3: a benchmark that needs an exact,
well-formed output (a compilable function, an instruction-following answer, a `####`-terminated
number) can lose that output entirely while the model still recognises the right answer among
four options.

* **Speed reward scales with model size**: +36% at 0.8B against **+93% at 9B**. Small models are
  already memory-bandwidth-bound at batch 1, so there is less headroom for the draft path to
  exploit; the bigger the model, the more the extra tokens per forward pass are worth.
* **MMLU is bit-identical at every draft depth on every model** (0.5241 / 0.6250 / 0.7456 /
  0.7939). That is not luck — MMLU is scored by log-likelihood over answer letters, and that path
  never invokes the draft model at all. It is the cleanest possible demonstration that the
  measurement is wired correctly, and it is a *positive control* rather than a null.
* The columns that *can* move — GSM8K, IFEval, HumanEval — move by **less than one item-level SE**
  (n = 50, 50, 164) and with no consistent sign on any model. There is no evidence of quality
  damage at these depths, and no evidence of a gain either.

**Practical reading**: turn MTP on, and use a depth around 4 — but expect the payoff to depend on
model size, and re-check it per model rather than assuming a fixed depth: the 2B *peaked* at depth
2 and regressed at 4, so "deeper is better" is false in general.

**Caveat that must travel with this table.** This axis can only run on the `-MTP-GGUF` repos: the
plain Qwen3.5 GGUF contains no MTP layers and `llama-server` refuses with "model doesn't contain
MTP layers". So the spec-decode models are a *different checkpoint family* from the rest of the
study and their absolute scores are not comparable to the quant-ladder rows.

### F8 — protocol choice flips the sign of quant conclusions (twice)

| case | protocol A | protocol B |
|---|---|---|
| Qwen3.5-9B `Q2→Q3` | HumanEval chat/thinking: **−0.073** (W2) | MultiPL-E raw completion: **+0.143** (m2) |
| Qwen3.5-4B tool calling | forced-JSON prompt: a "profile flip" (abstention ↑, multi-call ↓) (m4) | native `tools=`: uniformly better (+0.08) (m4b) |

**Any quant-effect claim is meaningless without naming its generation protocol.**

## 4. Practical answer for choosing a quant

1. **Default to ≥ Q3.** It was never significantly worse than Q2 in 13 anchors × (code, tools,
   multi-turn), and is usually much better (F1).
2. **Above Q3, only pay if you can measure a reason to.** For most Qwen/gemma checkpoints Q3 ≈ Q4 ≈
   Q5 on task scores; for granite, Q4 still helps (`Q3→Q4` pooled +0.078 [+0.002, +0.153],
   `m10-granite-q34`).
3. **Small models on agentic/long-horizon work need more headroom**: a 2B at Q2 collapses to ~0.005
   on every hard multi-turn category while Q3 recovers it (F3).
4. **At equal file size, the scheme can beat the level** (IQ > K, F4); match bytes/level, not the
   vendor label.
5. **Ignore PPL as a decision rule** — it disagrees with task score in ~30% of cases and can point
   the wrong way (F7).
6. **Re-measure on your own protocol.** The same weights look better or worse under chat vs raw, and
   forced vs native tool calling (F8).
